# Prototype acceptance matrix and owner evidence checklist

## Purpose and status

This is the acceptance contract for the current Windows WPF unified live-account browser prototype. It is not a production release. The current source implements two isolated persistent WebView2 account panes, visible-table inventory extraction, a native merged/searchable list, per-account refresh progress and typed outcome classification, bounded read-only console inspection, a local JSON inventory cache, and guarded Connect/official-client handoff. The repository source and synthetic tests do not prove compatibility with a live Splashtop console or a successful remote session.

At the historical inspected baseline `9826abe964e932abd49e0dab508a5f25bb6af9c6`, hosted Windows CI and source-defined smoke tests used synthetic local fixtures, not live account DOM evidence. The current published testing prerelease is `v0.3.8-test`, source commit `920545196c7868907992ff83473fd6b889b9acf5`. Its exact-commit Windows workflows and package are parent-verified; this still does not prove live account DOM compatibility, owner login/MFA, or a real remote-session outcome. Owner validation remains pending. Do not claim production readiness or live account acceptance.

Historical gates in older planning documents were explicitly deferred/superseded by the later prototype authorization. They remain useful as a record of the earlier development process, not as a current ban on the implemented WPF/WebView2 prototype. See `PROTOTYPE-AUTHORIZATION.md` for that direction. This acceptance list does not authorize account access by workers; the owner performs live validation locally.

## Current behaviors and hard boundaries

- Exactly two configured account panes are supported. Each uses a distinct persistent WebView2 profile and an official HTTPS console URL on `my.splashtop.com` or `my.splashtop.eu`, default port only. User signs in and completes MFA/SSO/device checks normally.
- The extractor reads supported visible table/grid columns (Name, Device Name, Group, Notes), row Connect control presence, and supported semantic status indicators. It does not derive status from colors or device names, and does not infer a numeric device identity that is absent from the rendered list.
- The unified list preserves rows per account; names are not a deduplication key. Search covers account label and displayed row fields. Refresh runs per account and reports progress; unknown totals remain indeterminate.
- `Complete` requires a reconciled reported row count, a verified pager walk to disabled Next when no total is available, or a bounded scroll walk that reaches the physical bottom and remains stable for two quiet 250ms intervals. Scrolled rows are tracked by their position in the content; repeated indistinguishable identities at different positions, failed/mismatched totals, timeouts, and ambiguous layouts remain incomplete. Scroll height alone is not proof, and incomplete/cache/stale inventory still cannot Connect.
- Status is a point-in-time read. Unknown remains unknown. Cached/last-read status is not monitoring or current presence.
- The allowlisted per-user JSON cache is at `%LOCALAPPDATA%\SplashtopUnified\AccountBrowser\inventory-cache.json`; it is not SQLite and not connection authority. Cached, stale, partial, failed or otherwise incomplete inventory cannot Connect. Current row positions and target are revalidated before action; account selection is bound to its owning pane.
- A Connect action requires a current eligible row, a host intent prompt, and the account's own official console action. Only options actually observed in its chooser may be selected. A Business-app URI handoff requires exact trusted HTTPS/default-port/top-document origin protections and owner confirmation; no guessed URI arguments or private APIs.
- Synthetic browser fixtures test extraction logic and handoff guards only. They are not Splashtop DOM and cannot count as live account validation.

## Evidence and reporting rules

1. Keep real inventories, identifiers, emails, hostnames, MACs, screenshots, credentials and raw WebView2/browser diagnostics on the owner's machine. Share only redacted counts/outcomes that are safe to disclose.
2. Label synthetic fixtures exactly as synthetic. They support deterministic code-path tests only and are not live console DOM evidence.
3. A successful CI job proves only commands/assertions it actually ran on its synthetic runner. It does not prove owner login/MFA, current DOM shape, complete real inventory, client handoff outcome, status freshness, or release acceptance.
4. Record failed, partial and NOT RUN items. Do not convert a plan, code review, process launch or URI handoff into a PASS for actual session outcome.
5. Parent owns final Windows CI and release verification. The exact `v0.3.8-test` CI and artifact evidence is recorded above. Owner-live acceptance and production readiness are not claimed.
