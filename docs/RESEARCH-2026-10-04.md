# Research and current-documentation review

**Reviewed:** 2026-10-04. **Purpose:** pre-implementation research for this Windows-only project. This is an engineering/compliance risk note, not legal advice. Splashtop documentation and Terms can change; check the live sources again before implementation and release.

## Findings supported by current sources

### Splashtop Business URI and shortcuts

Splashtop's RMM support documentation publishes this remote-session URI shape: `st-business://com.splashtop.business?account=email@example.com&mac=C04A001C72EC`. The account is supplied by email and the target is identified by MAC address; the article says subsequent URI launches can open the remote session through the Business app.[1] Splashtop's desktop-shortcut article independently documents the same URI form and says the portable and Windows Store Business app editions do not support custom desktop shortcuts.[2]

Splashtop documents UI-created shortcuts for Remote Connection, Remote Command and File Transfer, with licensing qualifications.[2] The reviewed manual URI documentation publishes the remote-session URI, but does not document URI arguments for Remote Command or File Transfer.[2] The project will not infer or reverse-engineer such arguments; those actions remain routed to the official web console unless Splashtop documents a supported URI.

**Not proven by documentation:** URI dispatch against the currently installed Windows client; exact target selection when MACs are shared; account/team selection when two teams use the same email; behavior when the Business client is closed; protocol registration; or account-specific limitations. These are Phase 1/2/5 live tests. No URI has been launched from this Linux agent environment.

### Multiple accounts and CSV

Splashtop documents adding more than one account to the Business app, selecting “Stay Logged In,” and switching accounts.[3] This documentation does not prove URI selection is unambiguous across same-email/multiple-team setups, nor that web-console sessions share browser data; both remain live-validation questions.

Splashtop documents an export action for the computer list under Management → All Computers.[4] The article does not enumerate the current export's columns.[4] Therefore, the CSV provider must accept nullable IDs/MACs and must not assume an actual export contains either; its real headers/rows need a sanitized user-supplied fixture before implementation is considered complete.

### Terms of Service — automated console use

The current Global Terms apply to users of the Global service region and link the EU Terms for the EU region.[5][6]

In the Global Terms' software restrictions, the reviewed text bars use/access for certain monitoring of the availability, performance or functionality of Splashtop Services/Software and competitive purposes; the service restrictions also bar collecting/storing third-party information without consent and using the Services in a way that may harm or disrupt Splashtop systems/accounts.[5]

The EU Terms contain corresponding restrictions.[6]

The Terms passages reviewed do not expressly name browser automation, DOM parsing, scraping, or scheduled web-console refresh.[5][6] That is not affirmative permission. This product would read and locally cache account inventory—including potentially identifying device names, users, notes and MACs—and periodically observe online/offline status. Whether that is authorized under a particular customer's agreement and the third-party-consent language is not established here.[5][6] The app should be restricted to the user's authorized account/session, minimize refresh/detail requests, avoid disruption and collection of unrelated information, and obtain written Splashtop/customer compliance guidance before broadly enabling automated recurring collection. No cookies/tokens may be exported or replayed; all reads stay inside the authenticated WebView2 page context as specified.

### Microsoft WebView2 and .NET

Microsoft documents multiple named WebView2 profiles under one user-data folder; each profile keeps separate browser data such as cookies, preferences and cached resources.[7] `CoreWebView2ControllerOptions.ProfileName` selects the profile for a controller.[10] This supports the proposed per-account profile architecture in principle, but does not replace the required Windows integration proof: cookies/storage isolation, new-device verification, persistence after restart, and concurrent logins are Phase 3 tests.

Microsoft documents `NewWindowRequested` for page-created windows and allows the host to supply a target WebView or handle the request.[8] The eventual account browser must route approved SSO/popup windows to a child WebView using the same account profile and still enforce origin/navigation restrictions. Microsoft documents `LaunchingExternalUriScheme` for requests to OS-registered URI schemes and gives the host the option to cancel them.[9] The implementation must allow only validated `st-business:` requests from approved Splashtop origins; no general protocol forwarding.

As of this review, Microsoft lists .NET 10 as the active LTS release (10.0.12 published 2026-09-08); .NET 11 was still Release Candidate 1, so it is not the stable target.[11] NuGet listed `Microsoft.Web.WebView2` 1.0.4258.31, published 2026-09-28, as the latest package version shown during this review.[12] Pin the then-current stable versions when the implementation phase begins; do not take a prerelease dependency merely because it is newer.

WPF remains the selected default: the user explicitly requires a Windows-native WPF/WebView2 application unless a strong technical reason justifies WinUI 3. No such reason has appeared in this documentation review. A compact native WPF device list also fits the requested separation between a primary technician UI and a small account-browser window.

## Not verified in this review

- Installed Splashtop Business version, protocol-handler registration or any remote session.
- Splashtop login/MFA/SSO/new-device verification behavior for these particular accounts.
- Same-email/two-team URI behavior or direct-vs-web Connect behavior.
- Current console region redirects, page rendering, component data, pagination counts, or live updates.
- MAC visibility in the permitted detail page, DOM, device rows or actual CSV export.
- Current UI connect button's external handoff behavior or shared-MAC orphan selection.
- Whether scheduled automated use is approved for this customer's account/tenant.

The detailed acceptance record belongs in [the Phase 5 validation report](VALIDATION-REPORT.md), which is intentionally still pending. Do not represent any of the above unknowns as tested facts.
